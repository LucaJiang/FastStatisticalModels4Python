Today is not about genetics. It's about a problem every scientific Python user hits: our code is too slow, and when we make it faster, how do we know it still gives the same answer? On the right are three numbers from this talk. A matrix rewrite that changes the p-values by exactly zero. Free-threaded Python 3.14 scaling threads by almost 5x. The problem

A readable permutation test is too slow at genomics scale

The reference: easy to read, easy to trust

for r in range(R):
    labels_r = rng.permutation(labels)
    null[r] = group_difference(X, labels_r)

p_values = (abs(null) >= abs(t_obs)).mean(axis=0)

X is n samples × p features. Every one of R shuffles touches all of X.

Server CPU, NumPy matrix path 10.7 s n = 5,000, p = 500,000, R = 5,000
Same server, bigger run > 45 min n = 50,000, p = 50,000, R = 100,000 timed out
Two questions How do we make it fast?
How do we prove nothing changed?
Here's the kind of code we start with. A permutation test: shuffle the group labels, recompute the statistic for every feature, repeat R times, and count how often the shuffled statistic beats the observed one. That count is the p-value. This code is good. It reads like the textbook definition, so we trust it. The problem is size. In genomics, p is hundreds of thousands of features and R is thousands of shuffles. Even after we vectorized it with NumPy, one test with half a million features takes about 11 seconds on our server. That sounds fine until you run it thousands of times in a simulation study. And one larger configuration didn't finish within our 45-minute limit at all. So we have two questions. How do we make this faster? And, as statisticians, the one we care about more: how do we prove the fast version answers the same question?
Our rule

Validate against a reference before timing anything

1Define the targetWhich statistic, which p-value, which estimate.
2Simulate dataKnown truth: nulls, effects, hard cases.
3Write a referenceSlow, readable, close to the math.
4Check equivalenceFast version matches the reference within tolerance.
5Measure the bottleneckLoops, dense algebra, or repeated work?
6Apply the smallest toolNumPy, Numba, threads, or GPU.

A faster version that changes the statistic gives you a wrong answer sooner.

Our rule is simple: validate first, then time. We define exactly what we're computing. We simulate data where we know the truth. We write a slow reference implementation that looks like the math. Every optimized version must match that reference before we look at its runtime. Only then do we measure where the time goes, and pick the smallest tool that fixes that bottleneck. Not the most exciting tool. The smallest one. The reason is in the orange box. If the fast version quietly changes the statistic, you haven't saved time. You've just produced a wrong scientific conclusion sooner.
For programmers

Simulation is how statisticians write tests

Real data has no answer key. Simulated data does.

Unit test
Fixed seed: fast and reference give the same numbers.
Property test
Under the null, p < 0.05 about 5% of the time.
Stress test
Outliers, imbalance, overlapping clusters, high dimension.
Load test
Grow n, p, and R until runtime or memory breaks.
Regression test
Every new engine re-passes all checks above.
If you write software, you already know this idea under a different name. Our outputs are random, so we can't assert one exact value. But we can still test. With a fixed seed, the fast and reference versions must agree: that's a unit test. Under the null hypothesis, a correct test rejects about 5 percent of the time at alpha 0.05: that's a property test. Outliers and imbalanced groups are stress tests. Growing the problem until it breaks is a load test. And every new engine has to pass all of this again: regression testing. So simulation gives statistical code an answer key. That's what makes optimization safe.
Two examples

Two workloads with different bottlenecks

k-means clustering

tight loopsdistance algebrasequential

Permutation tests

independent repeatsbatchingshared data
We use two workloads because they stress Python in different ways. k-means is iterative. Each step depends on the previous one, so you can't just run iterations in parallel. The cost is distance computations: N points times K centres times d dimensions, every iteration. A permutation test is the opposite. Every shuffle is independent, so it's embarrassingly parallel. The cost is R shuffles times the full data matrix, and with genomic p that gets very large. Different shapes, so we'll see different tools win.
Workload 1

k-means: an iterative fit

Check the method, check the code, then time it.

Let's start with k-means.
How it works

k-means alternates two steps until nothing changes

Lloyd's algorithm

  1. Start from fixed initial centres, so every engine begins in the same place.
  2. Assign each point to its nearest centre. This is the N × K × d distance work.
  3. Update each centre to the mean of its points.
  4. Stop when assignments no longer change.

Step 2 is the hotspot, and each iteration needs the previous one.

Here's k-means on the iris flower data. Each dot is a flower, plotted by petal length and width. We want three clusters. We start from fixed centres, so every implementation we compare starts from exactly the same place. Then two steps. Assign: each point goes to the nearest centre, and you can see colours change. Update: each centre moves to the mean of its points. We repeat until assignments stop changing. The assign step is where the time goes: every point against every centre in every dimension. And because each iteration needs the previous centres, we can parallelize inside an iteration but not across iterations.
Check the method first

Before speed: k-means fails on imbalanced clusters at any speed

Median adjusted Rand index (ARI) against simulated truth: 1 is perfect recovery, 0 is chance. MacBook Air simulation grid.

The first check isn't about code at all. Does the method recover the clusters we simulated? We score recovery with the adjusted Rand index: 1 means perfect, 0 means no better than chance. Rows are how well separated the clusters are; columns are different stressors. Clean, high-dimensional data: near-perfect, 0.9 to 1.0. But look at the two right columns. With a 90/10 imbalance in cluster sizes, recovery stays around 0.25 or lower, even when clusters are well separated. That is a property of k-means, not of our code. No amount of Numba or GPU fixes it. If this were our real data, we'd fix the method before optimizing anything. For this talk we accept these limits and move on to checking the code.

Three implementations

One assignment step, written three ways

NumPy

Turn distances into a matrix multiply.

x2 = (X**2).sum(1)[:, None]
c2 = (C**2).sum(1)[None, :]
d2 = x2 + c2 - 2 * (X @ C.T)
labels = d2.argmin(axis=1)

Wins when d and K are large enough for BLAS to shine.

Numba

Keep the loops, compile them.

@njit(parallel=True)
def assign(X, C, labels):
    for i in prange(len(X)):
        best = np.inf
        for k in range(len(C)):
            d = sqdist(X[i], C[k])
            if d < best:
                best = d
                labels[i] = k

Wins when the work is many small loops; no N × K temporary.

JAX

Same algebra, compiled for a GPU.

@jax.jit
def assign(X, C):
    x2 = (X**2).sum(1)[:, None]
    c2 = (C**2).sum(1)[None, :]
    d2 = x2 + c2 - 2 * (X @ C.T)
    return d2.argmin(axis=1)

Wins when there is enough regular work to pay for transfer.

Here is the hot step written three ways. NumPy: we expand the squared distance into x squared plus c squared minus 2 x dot c. The expensive part becomes one matrix multiply, which goes to an optimized BLAS library. Numba: we keep the explicit loops, which is closest to the textbook, and Numba compiles them to machine code and runs the outer loop in parallel. No big temporary matrix. JAX: almost the same code as NumPy, but jit-compiled to run on the GPU. All three passed the equivalence check on the previous slide. The question now is which one is fastest, and the answer depends on the shape of the data.

Workload 2

Permutation tests: many independent repeats

Rewrite the math, prove it's the same test, then scale it.

Now the permutation test, the example we started with.
How it works

Shuffle the labels many times to build the null distribution

One permutation test

  1. Compute the observed group difference for each of p features.
  2. Shuffle the A/B labels; X stays fixed.
  3. Recompute all p differences.
  4. Repeat R times. The p-value is how often shuffled beats observed.

Work grows as R × n × p.

Here's the permutation test in pictures. Each row is a sample, each column a feature, and samples belong to group A or B. We compute the observed difference between groups for every feature. Then we shuffle the labels, keeping the data fixed, and recompute every difference. That gives one draw from the null distribution: what differences look like when group membership doesn't matter. Repeat R times. The p-value for each feature is the fraction of shuffles that beat the observed value. The shuffles are independent, which is good for parallelism. But each one touches the whole matrix, so work grows with R times n times p.
Rewrite the math

Each shuffle is a weight vector, so a batch is one matrix multiply

Reference: one shuffle at a time

for r in range(R):
    null[r] = group_diff(X, perms[r])

Stores an R × p null matrix.

Optimized: a batch of shuffles at once

for W in contrast_batches(perms):
    T = W @ X          # batch × p
    counts += abs(T) >= abs(t_obs)

Keeps only p running counts.

A difference in group means is a weighted sum: weight +1/nA for group A, −1/nB for group B. Stack one weight row per shuffle into W (batch × n). Then W @ X gives every statistic for the batch, and BLAS or a GPU does the work.

This is the key rewrite. A difference in group means is just a weighted sum of the rows: plus one over n A for samples in group A, minus one over n B for group B. So each shuffle is a weight vector. Stack a batch of them into a matrix W, and W times X gives you the statistics for the whole batch in one matrix multiply. That's exactly the operation BLAS and GPUs are built for. The second change is streaming. The reference stores the full R by p null matrix, which for half a million features doesn't fit in memory. The optimized version keeps only a running count per feature: how many shuffles beat the observed value so far. The math is the same. The shape of the computation is completely different. That's why we have to prove it's still the same test.

Statistics differ only by floating-point rounding. Because counts are compared to the same threshold, p-values match exactly.

First check: does the rewrite produce the same numbers? Both versions get the same data and, importantly, the same sequence of shuffles. Otherwise we'd be comparing random noise. We ran 18 different problem shapes, each with 5 seeds: 450 comparisons passed, none failed, and 45 were skipped because the reference would have run out of memory. The p-values matched exactly: maximum difference zero. The statistics differed by at most 10 to the minus 16, which is rounding in the last bit of a double. We set a tolerance of 10 to the minus 6 before running anything, and we're ten orders of magnitude inside it. So the code is equivalent. But equivalent code can still implement a bad test, which brings us to the second check.

Second check: is it a valid test? Equivalence tells us the fast code matches the slow code. It doesn't tell us the slow code was right. So we simulate data where there is no real difference between groups. A correct test at alpha 0.05 should flag about 5 percent of features, purely by chance. We observed 0.051. The dashed line is 0.05, the dot is our estimate, and the green band is the range you'd expect for a single feature just from binomial noise. When to use a GPU

The A100 pays off once R × p is large: up to 8.5× faster

Speedup = server CPU matrix time ÷ A100 streamed time, n = 5,000, both end to end. Transfer included, JIT compile excluded. Best cell: 10.7 s → 1.25 s.

Now speed. This map compares our server CPU against an A100 GPU, running the same validated, streamed permutation test. Columns are the number of features, rows the number of shuffles. Each cell is how many times faster the GPU is, end to end, including copying data to the GPU. Bottom left, the smallest problem: the CPU wins. The GPU is 0.7 times as fast because transfer and launch overhead dominate. As p and R grow, the GPU pulls ahead. The best cell, half a million features and 5,000 shuffles, goes from 10.7 seconds to 1.25 seconds: 8.5 times faster. Top right, grey: the GPU ran out of memory. The CPU still finished. So even the GPU has a shape it doesn't fit. The lesson: the GPU is worth it only when there's a lot of regular work. And it only helped because we had already rewritten the test as a matrix multiply.
CPU parallelism

More workers help until about 16, then stop paying

Big early win1 → 4 workers saves 58% (k-means) and 46% (permutation).
Then flat or worsePermutation is slower at 64 and 128 workers than at 16.
Memory explodes128 process workers each copy the data: 58 GiB peak.
What about plain CPU parallelism on the server? Going from one to four workers is a big win: 58 percent faster for k-means, 46 percent for the permutation test. After that, each doubling buys less. For the permutation test, going past 16 workers actually made it slower. And look at memory. The permutation version uses processes, and each process gets its own copy of the data. At 128 workers that's 58 gigabytes. So: take the early speedup, then stop. And that memory cost is exactly what free-threaded Python addresses.
Python 3.14

Free-threaded Python 3.14t lets threads scale: 4.77× on 16 threads

Standard CPython 3.14 1.02× 1 → 16 threads. The GIL lets one thread run Python at a time.
Free-threaded 3.14t 4.77× Same code, same threads. 0.57 s → 0.12 s.
Threads vs processes 2.43× faster
32% less memory 3.14t ThreadPool vs standard ProcessPool. One shared copy of the data.

Pure-Python, CPU-bound resampling over shared in-memory data. Your speedup depends on how much of your work runs as Python bytecode.

This is the Python 3.14 part of the talk. Here's a CPU-bound resampling workload written in plain Python, run with a ThreadPoolExecutor. On standard CPython 3.14, the grey line: 16 threads are no faster than one. That's the GIL: only one thread executes Python at a time. Same code on the free-threaded build, 3.14t, the blue line: 16 threads are 4.77 times faster. Nothing changed in our code. Only the interpreter. The usual workaround for the GIL is processes. But processes copy the data, which is the 58 gigabytes we saw on the last slide. Compared with a ProcessPool on standard Python, threads on 3.14t were 2.4 times faster and used a third less memory, because all threads share one copy. A caveat: this helps code that spends its time in Python bytecode. If your hot loop is already inside NumPy or BLAS, those release the GIL anyway, and you'll see less difference. And as always, we re-ran the validation on 3.14t.

Here's everything in one slide. If your profile shows tight numerical loops, try Numba. If the math can be written as matrix products, rewrite it and let NumPy and BLAS do the work. If you have many independent repeats over shared data, threads on free-threaded Python are now a real option. And if you have huge, regular batches, a GPU with JAX can pay off, but only once the work outweighs the cost of moving data. I think of it like travel. You don't fly across Victoria Harbour, and you don't walk to Tokyo. You look at the trip first, then pick the vehicle. Here the trip is your bottleneck, and the only way to know it is to measure. And every row assumes the validation already passed. Speed is the last step.
AI coding tools

AI speeds up writing fast code. It doesn't skip the validation.

What AI made faster

  • Translating the NumPy reference into Numba and JAX: a first draft in minutes, not a day.
  • Trying more variants than we would have written by hand.
  • Experiment runners, metadata logging, and figure regeneration.

What stayed the same

  • AI output is one more candidate. It passes the same checks as hand-written code.
  • Equivalence against the slow reference, same seeds, tolerance fixed in advance.
  • Calibration under the null.
  • Only then, end-to-end timing. Kernel-only GPU numbers looked faster, so we excluded them.

Generating code got cheap. Trusting it still costs a reference and a test.

We used AI coding agents a lot in this project, and they really did speed us up. Translating a NumPy reference into Numba or JAX used to take us a day; an agent gives a working first draft in minutes. That means we tried more variants than we ever would have written by hand. It also built the experiment runners and regenerated the plots. But notice that nothing in our rule changed. To us, AI-written code is just one more candidate implementation. It goes through exactly the same steps as code we write ourselves: match the slow reference on the same seeds, within a tolerance we fixed before looking; check calibration under the null; and only then measure end-to-end time. One small example. The agent's GPU timings for the kernel alone looked much better than our end-to-end numbers. They were real numbers, but they skip copying data to the GPU, so they answer a different question. We left them out. So AI makes writing fast code cheaper. It doesn't make trusting that code any cheaper. That still takes a reference and a test, which is the whole point of this talk.

This backup slide is about the trend, not a proof of optimality. batch_R is the number of permutation rows processed in one A100 batch. In this committed sweep, small batches were slower because the streamed path paid more scheduling and loop overhead. Increasing batch_R reduced that overhead, but the gains flattened after roughly 512-1024 and the curve is not perfectly monotone. 8192 was the fastest accepted value in the measured 128-8192 grid, so it was used as the chosen setting for the later A100 decision map. Larger batch_R values were not part of this committed sweep; they could be faster, slower, or fail because of memory or autotuning. batch_R changes scheduling, not the permutation statistic or p-value definition.
