Source: experiments/results/v2/kmeans_sweep.csv. All impls agree on inertia to < 1 ULP at identical init. JAX includes block_until_ready.

Narrative: matmul distance loses to broadcast at tiny (K=5, d=10) because the BLAS call is too skinny to pay for the norm computations. At K≳50 / d≳100 (typical EM), matmul flips and wins. Numba is the most reliable speedup on CPU; JAX matches it at N=1M. Small-N JAX is held back by per-call dispatch, not compute.

k-means takeaways

  • Smart NumPy ≠ faster NumPy. Matmul-distance only pays off when K × d is big.
  • Numba: 10× over naive NumPy at N=1M with a drop-in refactor. Our most reliable CPU lever.
  • JAX catches Numba at N=10⁶ on CPU; its real story is "same code, GPU speedup for free".
  • Pure Python loops are 2 orders of magnitude off — that's the headroom the 3.14 JIT aims at.

Bridge to second half: different bottleneck—parallel resampling and memory copies.

Permutation test (sketch)

  • Concatenate two groups into x (length n), split index n1.
  • Statistic: difference of means after permuting indices.
  • Repeat R times → empirical null distribution.

Implementations: experiments/permutation_test/

Emphasize independence across permutations—perfect for parallel patterns.

The algorithmic move before we parallelise

Observe that sum(x) is constant:


stat = S1/n1 − (S − S1)/n2         # S = sum(x)   (fixed)
     = S1 × (1/n1 + 1/n2) − S/n2

So the statistic depends only on the subset sum S1. We can replace a full rng.permutation(n) with rng.choice(n, n1, replace=False) — "pick which n1 indices go to group A".

Caveat we measured: in plain NumPy, rng.choice(..., replace=False) is implemented via permutation, so the naive trick buys nothing — but the batched form (argpartition) turns the idea into a real 2.6× speedup.

This is the talk's most useful transferable idea: attack the statistic before the compute. Works for bootstrap, bagging, and anywhere the aggregator is linear.

Source: experiments/results/v2/perm_sweep.csv · children RSS is a psutil probe during the run.

Three surprises for the audience: (a) the algorithmic "trick" doesn't pay by itself because np.random.choice(replace=False) is permutation-based — but it saves 2× in the batched form; (b) on a GIL build threads still give 1.4× because NumPy releases the GIL inside .sum() / .permutation() — a good motivator for free-threaded 3.14; (c) JAX vmap on CPU is a genuine anti-pattern for this workload.

Permutation takeaways

  • Numba prange: one process, one copy, 13× over naive NumPy — the single best ROI on CPU.
  • Threads on GIL build already give 1.4× (NumPy releases the GIL). Free-threaded 3.14 should widen this further.
  • multiprocessing pays a ~3 s startup and holds ~100 MiB per worker — mind copies on big arrays.
  • Batched NumPy trades 2 GiB of RAM for a memory-bandwidth loss. Not a free win.
  • JAX vmap on CPU: honest anti-pattern for this kernel; reserve for accelerators.

Briefly mention reproducibility: parallel RNG ordering — use SplitMix-style per-iter seed mixing (we burned an hour on a 0.05σ drift from a correlated LCG).

Developer experience

  • Start simple: correct NumPy first.
  • Profile: prove the hotspot before rewriting.
  • AI as copilot: great for translating math→NumPy→Numba/JAX—still verify numerics.

~2 minutes. Connect to collaboration and reproducibility priorities in statistics.

Decision guide

Small Numba refactor fixes hot loops Often the best ROI on CPU numerical code.
CPython 3.14 JIT Low-effort speedups for Python-heavy glue; not a substitute for vectorized NumPy.
Free-threaded 3.14 Consider when threads + shared big arrays beat multiprocessing copies.
JAX When functional style + XLA/GPU/TPU batching matches your workload.

Close the loop: extra complexity must buy measurable wins for your team.
