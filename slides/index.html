A quick word about me. I'm a PhD student in biostatistics at City University of Hong Kong. I work on statistical genetics and genomics, where the data are really big like hundreds of thousands of genetic variants and genes. I recently finished prusie, a Python package with a Rust core that reimplements a R package. On 200 GWAS loci, the R package takes almost two hours; prusie takes under three minutes. On 14k genes dataset, it reduce the runtime from 21 hours to 48 minutes. It also reduces peak memory use by about 80%. It's faster and uses less memory. Most importantly, although there are small numerical differences from reference, the key statistical features remain the same. That is what this talk is about: making statistical code fast while proving it still gives the same answer. Today I'll use two simpler examples, k-means and permutation tests, so we can walk through every step.
The problem

A readable permutation test is too slow at genomics scale

The reference: easy to read, easy to trust

for r in range(R):
    labels_r = rng.permutation(labels)
    null[r] = group_difference(X, labels_r)

p_values = (abs(null) >= abs(t_obs)).mean(axis=0)

X is n samples × p features. Every one of R shuffles touches all of X.

Two questions How do we make it fast?
How do we prove nothing changed?
Here's the kind of code we start with. A permutation test: we have a group of labels, shuffle the group labels with rng.permutation, compute the statistic we call null, repeat it R times, and count how often the shuffled statistic beats the given one. That count is the p-value. This code is good. It follows the textbook definition, so we trust it. The problem is size. In genomics, p is hundreds of thousands of features and R is thousands of shuffles. Even after we vectorized it with NumPy, one test with half a million features takes about 11 seconds on our server. That sounds fine until you need to run it thousands of times. Also, as the size goes larger, we can find that it can not finish within 45-minute. So we have two questions. How do we make this faster? And, as statisticians, we care about that: how do we prove the fast version answers the same question?
Our rule

Validate against a reference before timing anything

1Define the targetWhich statistic, which p-value, which estimate.
2Simulate dataKnown truth: nulls, effects, hard cases.
3Write a referenceSlow, readable, close to the math.
4Check equivalenceFast version matches the reference within tolerance.
5Measure the bottleneckLoops, dense algebra, or repeated work?
6Apply the suitable toolNumPy, Numba, threads, or GPU.

Speed matters, but statistical correctness matters more.

Our rule is simple: validate first, then measure performance. First, we define what we want to compute and how to evaluate the results. We simulate data, so we know the ground truth. Then we write a simple, slow reference implementation that follows the math. Before testing speed, every optimized version must agree with the reference, within a small numerical tolerance. We also check that the key statistical results stay the same. Only after that do we measure where the time goes and choose the right tool to speed up the bottleneck.
For programmers

Simulation is how statisticians write tests

Simulations provide known ground truth for validation.

Unit test
Fix the seed; compare each function with a simple reference.
Property-based test
Generate many datasets; check expected statistical properties.
Edge-case test
Try outliers, imbalanced groups, and other unusual cases.
Load test
Increase data size and measure runtime and memory.
Stress test
Push beyond normal limits to find where the program fails.
Regression test
Rerun these checks after every code change.

Simulation helps us check correctness before we focus on speed.

If you write software, you probably know these ideas by different names. In statistics, we often work with random data, and optimized code may produce small numerical differences. So we cannot always expect an exact match. But we can still test the code. With a fixed seed, we can reproduce the same data. We compare individual functions with a simple reference. That's unit testing. We generate many datasets and check properties that should always hold. That's property-based testing. We test unusual cases, like outliers and imbalanced groups. Those are edge-case tests. We increase the data size to see how the program performs. That's load testing. We push the program beyond its normal limits. That's stress testing. And after every code change, we run these tests again. That's regression testing. So simulation helps us check correctness before we focus on speed.

We use two examples because they have different performance bottlenecks. First, k-means. It runs in iterations, and each iteration depends on the previous one. So we cannot run all iterations in parallel. But within each iteration, we can calculate distances in parallel. For N data points, K cluster centers, and d dimensions, the cost is roughly N times K times d per iteration. Second, a permutation test. Each permutation is independent, so we can run many of them in parallel. We repeat the calculation R times, often across many variables. When R and p are large, the cost can be very high. These two workloads have different bottlenecks, so different optimization tools may work best.
Workload 1

k-means: an iterative fit

Check the method, check the code, then time it.

Let's start with k-means.
How it works

k-means alternates two steps until nothing changes

Lloyd's algorithm

  1. Start from fixed initial centres, so every engine begins in the same place.
  2. Assign each point to its nearest centre. This is the N × K × d distance work.
  3. Update each centre to the mean of its points.
  4. Stop when assignments no longer change.

Step 2 is the hotspot, and each iteration needs the previous one.

Here's k-means on the Iris dataset. Each dot represents a flower, based on its petal length and width. The dataset has three known species, so we set the number of clusters to three. We use the same starting centers for every implementation, to make the comparison fair. Then we repeat two steps. First, assign each point to its nearest center. You can see the colors change. Second, update each center by taking the mean of its assigned points. We repeat these steps until the assignments stop changing. Most of the computation happens in the assignment step, because we need to calculate the distance from every point to every center. And because each iteration depends on the previous one, we can run calculations in parallel within an iteration, but the iterations themselves must run in order.
Check the method first

Before speed: k-means fails on imbalanced clusters at any speed

Median adjusted Rand index (ARI) against simulated truth: 1 is perfect recovery, 0 is chance. MacBook Air simulation grid.

First, we check the statistical performance. Can k-means recover the clusters we simulated? We measure this using the adjusted Rand index, or ARI. A score of 1 means perfect recovery, while 0 means about the same as random guessing. The rows show different levels of cluster separation, and the columns show different data conditions. On clean, high-dimensional data, the results are very good, with ARI between 0.9 and 1.0. But look at the two columns on the right. When cluster sizes are imbalanced, with a 90-to-10 ratio, ARI drops to around 0.25 or lower, even when the clusters are well separated. This shows a limitation of k-means itself. Making the code faster with Numba or GPU won't solve this problem. In real research, we should address this statistical limitation first. For this talk, we'll keep it in mind and move on to checking our implementations.

Three implementations

One assignment step, written three ways

NumPy

Turn distances into a matrix multiply.

x2 = (X**2).sum(1)[:, None]
c2 = (C**2).sum(1)[None, :]
d2 = x2 + c2 - 2 * (X @ C.T)
labels = d2.argmin(axis=1)

Wins when d and K are large enough for BLAS to shine.

Numba

Keep the loops, compile them.

@njit(parallel=True)
def assign(X, C, labels):
    for i in prange(len(X)):
        best = np.inf
        for k in range(len(C)):
            d = sqdist(X[i], C[k])
            if d < best:
                best = d
                labels[i] = k

Wins when the work is many small loops; no N × K temporary.

JAX

Same algebra, compiled for a GPU.

@jax.jit
def assign(X, C):
    x2 = (X**2).sum(1)[:, None]
    c2 = (C**2).sum(1)[None, :]
    d2 = x2 + c2 - 2 * (X @ C.T)
    return d2.argmin(axis=1)

Wins when there is enough regular work to pay for transfer.

Here is the same k-means assignment step, implemented in three different ways. First, NumPy. We rewrite the squared distance as x squared plus c squared minus two times x dot c. This turns most of the work into matrix multiplication, which uses an optimized BLAS library. Second, Numba. We keep the simple loops, just like the original algorithm. Numba compiles them into machine code and runs the loop over data points in parallel. This also avoids creating a large distance matrix. Third, JAX. The code looks similar to NumPy, but we use JIT compilation to run it on the GPU. All three implementations matched the reference in our tests. Now the question is: which one is the fastest? As we'll see, the answer depends on the size and shape of the data.

So, which one is the fastest? Let's look at three different problem sizes on our server. First, a small problem. All three versions finish in less than half a second. The differences are very small, so there's usually no need to spend time optimizing further. Second, a larger problem: one million data points, 256 dimensions, and 50 clusters. Workload 2

Permutation tests: many independent repeats

Rewrite the math, prove it's the same test, then scale it.

Now the permutation test, the example we started with.
How it works

Shuffle the labels many times to build the null distribution

One permutation test

  1. Compute the observed group difference for each of p features.
  2. Shuffle the A/B labels; X stays fixed.
  3. Recompute all p differences.
  4. Repeat R times. The p-value is how often shuffled beats observed.

Work grows as R × n × p.

Here is how the permutation test works. Each row is a sample, each column is a feature, and each sample belongs to group A or group B. First, we calculate the difference between the two groups for each feature. Then we randomly shuffle the group labels, keeping the data unchanged, and calculate the differences again. We repeat this R times to build a null distribution. This shows what differences we might see if the group labels didn't matter. For each feature, the p-value tells us how often the shuffled results are at least as extreme as the observed result. Each shuffle is independent, so we can easily run them in parallel. But if every shuffle processes the full data matrix, the total work grows with R times n times p.
Rewrite the math

Each shuffle is a weight vector, so a batch is one matrix multiply

Reference: one shuffle at a time

for r in range(R):
    null[r] = group_diff(X, perms[r])

Stores an R × p null matrix.

Optimized: a batch of shuffles at once

for W in contrast_batches(perms):
    T = W @ X          # batch × p
    counts += abs(T) >= abs(t_obs)

Keeps only p running counts.

A difference in group means is a weighted sum: weight +1/nA for group A, −1/nB for group B. Stack one weight row per shuffle into W (batch × n). Then W @ X gives every statistic for the batch, and BLAS or a GPU does the work.

Here is the key optimization. The difference between two group means can be written as a weighted sum. Each sample in group A gets a weight of one over n A, and each sample in group B gets minus one over n B. So each shuffle gives us a different weight vector. We can combine many weight vectors into a matrix W. Then, W times X calculates the test statistics for the whole batch using just one matrix multiplication. This is exactly what BLAS and GPUs are good at. The second optimization is memory usage. The reference stores the results of all R permutations for all p features. When we have half a million features, this can use a lot of memory. Instead, we process the permutations in batches and keep a running count for each feature. We only need to count how many shuffled results are at least as extreme as the observed result. The statistical test stays the same, but the computation is very different. So we need to check that the optimized results still match the reference.

Now the second check: is the statistical test itself correct? We already showed that the fast version matches the reference. But we also need to check whether the test gives reliable results. We simulate data where there is no real difference between the two groups. With a significance level of 0.05, a well-calibrated test should reject the null hypothesis about 5 percent of the time. In our simulations, the rejection rate was 5.1 percent, very close to the expected 5 percent. The difference is within the range we'd expect from random variation. So we have two checks: the optimized code matches the reference, and the statistical test gives the expected false-positive rate under the null. Now we can move on to performance.
When to use a GPU

The A100 pays off once R × p is large: up to 8.5× faster

Speedup = server CPU matrix time ÷ A100 streamed time, n = 5,000, both end to end. Transfer included, JIT compile excluded. Best cell: 10.7 s → 1.25 s.

Now let's look at speed. This heatmap compares our server CPU with an A100 GPU, using the same permutation test. The columns show the number of features, and the rows show the number of shuffles. Each cell shows how much faster the GPU is compared with the CPU. We measure the total runtime, including data transfer to the GPU. For the smallest problem, the CPU is faster. The GPU is only 0.7 times as fast, because the overhead is larger than the time saved. But as the number of features and shuffles increases, the GPU becomes faster. In the best case, with half a million features and 5,000 shuffles, the runtime drops from 10.7 seconds to 1.25 seconds. That's about 8.5 times faster. The grey cell in the top right means the GPU ran out of memory, while the CPU could still finish. So GPUs work best when there is enough parallel work. And our matrix rewrite makes it possible to use the GPU efficiently.

Now let's look at CPU parallelism on our server. Going from one to four workers makes a big difference. K-means runs 58 percent faster, and the permutation test runs 46 percent faster. But adding more workers gives smaller improvements. For the permutation test, using more than 16 workers actually makes it slower. Now look at memory usage. Our permutation test uses multiple processes, and in our implementation, each process has its own copy of the data. With 128 workers, memory usage reaches 58 gigabytes. So more workers are not always better. We need to balance speed and memory usage. This is where free-threaded Python becomes interesting. It allows multiple threads to run in parallel while sharing data in the same process. Let's see how that works.

Pure-Python, CPU-bound resampling over shared in-memory data. Your speedup depends on how much of your work runs as Python bytecode.

Now let's look at Python 3.14. Here's a CPU-bound resampling task written in plain Python. On standard Python, 16 threads are no faster than one because of the GIL. But with the same code on free-threaded Python 3.14t, we get a 4.77 times speedup. Compared with a process pool on standard Python, it's 2.4 times faster and uses about one-third less memory, because threads can share data. This mainly helps CPU-bound Python code. NumPy and BLAS often release the GIL already, so the benefit may be smaller. And of course, we also validated the results on 3.14t.

Here's a simple guide to choosing the right tool. For numerical loops, try Numba. For matrix operations, use NumPy and BLAS. For independent tasks that share data, consider free-threaded Python. For large, parallel workloads, JAX on GPU may be the best choice. Think of it like travel. You wouldn't fly across Victoria Harbour or walk to Tokyo. You choose the right tool for the trip. And remember, all these choices come after validation.

This backup slide is about the trend, not a proof of optimality. batch_R is the number of permutation rows processed in one A100 batch. In this committed sweep, small batches were slower because the streamed path paid more scheduling and loop overhead.
