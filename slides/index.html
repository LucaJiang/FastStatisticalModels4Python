Welcome everyone. Today, we are discussing how to safely push the speed limits of statistical Python. In fields like genetics, speed is an absolute necessity. The human genome has millions of variants. When we test their relationships to a disease using resampling methods, we routinely execute billions of calculations. Without extreme optimization, a single experiment can take months. So, we must write fast code. But there is a strict rule: we cannot sacrifice statistical validity. If an optimized engine slightly changes the math, we are simply producing the wrong scientific conclusion faster. Today, we will explore a framework to prevent that.

Array expression on device.

@jax.jit
def assign(X, C):
    x2 = sumsq(X)[:, None]
    c2 = sumsq(C)[None, :]

    dist2 = x2 + c2 - 2 * (X @ C.T)
    return jnp.argmin(dist2, axis=1)

Mathematically, these three implementations are identical. Numba compiles explicit `for` loops to C-speed. NumPy flattens the logic into dense linear algebra. JAX mirrors NumPy, but compiles directly to the GPU using the `@jax.jit` decorator.

Execution model matters next.

When the GPU fails, we utilize CPU parallelism. Historically, Python relies on `multiprocessing`. The fatal flaw here is memory duplication. If you scale up workers on a large matrix, you copy the dataset until the server crashes.
EXECUTION MODEL

Free-threaded CPython changes this workload’s tradeoff.

Threads become viable when the workload is designed for shared-memory parallelism.

Standard GIL builds ~1.02× 1 → 16 workers py314 stays flat
CPython 3.14t / free-threaded 4.77× 1 → 16 workers threads scale this workload
Execution-model payoff 2.43× faster 32% less peak RSS ThreadPool vs ProcessPool

Official term: free-threaded CPython build, available since Python 3.13; supported but optional, not default.

It can run Python threads on CPU cores in parallel; C extensions may re-enable the GIL, and single-thread overhead exists.

This is why Python 3.13's Free-threaded build is a breakthrough. We bypass the Global Interpreter Lock. On standard Python, adding threads yields zero speedup. On the free-threaded build, threads scale linearly. We achieve parallel execution on one shared dataset, reducing peak memory by 32 percent.

Backup: what batch_R tuning showed

Larger batches amortized overhead; 8192 was fastest only within this measured grid.

Timing improved most at small batch_R; after 512-1024 the curve mostly flattened. 8192 is the fastest accepted value measured here.

Definition batch_R = permutation rows processed in one A100 batch.
Trend Small batches were slower; larger batches reduced stream overhead.
Diminishing returns Most of the gain appeared by 512-1024; later points were nearly flat.
Claim boundary 8192 was fastest in this measured grid. Larger values were not tested here.
batch_R tunes pipeline overhead; it does not change the statistical question.
This backup slide is about the trend, not a proof of optimality. batch_R is the number of permutation rows processed in one A100 batch. In this committed sweep, small batches were slower because the streamed path paid more scheduling and loop overhead. Increasing batch_R reduced that overhead, but the gains flattened after roughly 512-1024 and the curve is not perfectly monotone. 8192 was the fastest accepted value in the measured 128-8192 grid, so it was used as the chosen setting for the later A100 decision map. Larger batch_R values were not part of this committed sweep; they could be faster, slower, or fail because of memory or autotuning. batch_R changes scheduling, not the permutation statistic or p-value definition. Full end-to-end timing remains the criterion: compile excluded, transfer included, kernel-only excluded.
