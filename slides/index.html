Breaking the Speed Limit

Fast statistical models with Python 3.14, Numba, and JAX, told as a simulation workflow rather than a tool ranking.

Wenxin Jiang & Jian Yin · Department of Biostatistics, City University of Hong Kong

One sentence

Clear enough to trust. Fast enough to scale.

13.4x Numba prange vs NumPy loop on permutation, local CPU
0.17s free-threaded Python thread pool, R=10,000

Hi everyone, I am Wenxin Jiang, and this talk is about making statistical Python code clear enough to trust and fast enough to scale. The title says speed, and we will talk about Python 3.14, Numba, and JAX, but the real story is not a tool ranking.

The real story is a workflow. In statistics, we usually do not start with a perfectly optimized kernel. We start with a scientific question, a simulation that we control, and a reference implementation that we can reason about. Only after that do we ask which part is actually expensive and which tool should remove that bottleneck. By the end, I want you to leave with a practical mental model for choosing between plain NumPy, Numba, JAX, processes, threads, and free-threaded Python.

Opening Frame

Statistical code starts with trust, not speed

In statistics, the specification is often discovered through simulation. We build controlled worlds, write a clear reference, search for failures, then scale only after the behavior makes sense.

Controlled data

Known signal, known null, fixed seeds, small enough to inspect.

Reference code

Close to the math, readable, slow if necessary.

Failure modes

Noise, imbalance, bad seeds, high dimension, memory pressure.

Scale-up

Increase N, d, K, repetitions, and record runtime plus memory.

Optimize

Accelerate the pattern simulation proves is expensive.

Let me start from the way a statistician thinks about an experiment. If you come from software engineering, you can think of this as a mixture of unit tests, property tests, and load tests, but with a statistical target.

First we generate controlled data. We know the signal, the null model, and the random seed. Then we write reference code that is close to the math, even if it is slow. Then we deliberately look for failure modes: noise, imbalance, high dimension, bad seeds, and memory pressure. Only then do we scale up N, d, K, or the number of resamples, measure runtime and memory, and optimize the pattern that is proven to matter.

This ordering is important. If we optimize before we know what result to trust, a faster implementation can simply give us the wrong answer faster.

For the rest of the talk, I will keep coming back to this loop. Whenever I show a performance number, the question behind it is not only, how fast is this? The question is, did we keep the statistical meaning fixed while changing the implementation?

Why programmers should care

Ground truth is synthetic

Real data rarely has labels or exact answers. Simulation gives us a controlled environment to check behavior.

Failure can be statistical

A wrong p-value may be a bug, an invalid permutation scheme, or a method assumption breaking down.

Performance pressure is real

Resampling and iterative algorithms turn clear code into millions of repeated numerical operations.

A fast implementation that changes the statistic is not an optimization. It is a different method.

Why should programmers care about this framing? Because many performance bugs in statistical code do not look like ordinary software bugs. Real data rarely tells us the exact answer. If I run a clustering algorithm on patient data, I usually do not have a label that says this is the correct clustering. If I run a permutation test, I do not get a compiler error when the null distribution is wrong.

Simulation gives us a controlled world where we know what should happen. That makes it possible to separate three things that are often mixed together: implementation bugs, statistical assumptions, and performance bottlenecks.

The point on this slide is the rule for the whole talk. A fast implementation that changes the statistic is not an optimization. It is a different method. Sometimes a different method is fine, but then we should name it honestly.

Two workloads, two pressure points

Minimal statistics background required: we focus on computational patterns and validation discipline.

I will use two workloads. The first is k-means. I am not choosing it because it is the most advanced statistical model. I am choosing it because Lloyd's algorithm is simple enough to explain quickly, but it has the same shape as many iterative methods: assign, update, repeat. That gives us loop overhead, temporary arrays, cold-start compilation, and high-dimensional scaling.

The second workload is a permutation test. Here the statistic is very simple, but we repeat it thousands of times under random resampling. That exposes a different pressure point: process copies, shared memory, random number generation, and thread-level parallelism.

So the talk has one iterative workload and one resampling workload. The goal is not to prove a universal winner. The goal is to learn which tool fits which computational shape.

Before we look at numbers, here is the benchmark contract. All of the main local results come from the py312 environment: Python 3.12.2, NumPy 1.26.4, Numba 0.59.1, and JAX 0.4.25 on CPU. I also tested two Python 3.14 environments. The standard 3.14 build exposes sys._jit, but on this machine is_available is false, so I am not going to pretend I measured JIT speedups. The py314t environment is free-threaded, and sys._is_gil_enabled is false.

The measurement rules also matter. I report warm medians after a separate cold first call. Each implementation runs in a fresh subprocess, because memory allocators and JIT state can contaminate a benchmark. For JAX, timings explicitly call block_until_ready. For memory, I use tracemalloc for Python-visible memory and child RSS for multiprocessing, because process memory does not show up in the parent process.

This is not meant to be the final word on every machine. It is meant to be a reproducible local experiment with clear limits. If you run this on a GPU, or on a different BLAS library, some numbers will move. The interpretation should still be grounded in the same contract: same workload, same reference behavior, same measurement rules.

Workload 1

k-means as iterative simulation pressure

The algorithm is simple enough to explain in one slide, but it exposes loop overhead, temporary arrays, cold-start cost, and high-dimensional scaling.

Let us start with k-means. If you have not used it recently, the algorithm is straightforward. Given data points and K centroids, assign every point to the nearest centroid, then recompute the centroids as the mean of the assigned points. Repeat until convergence or until a maximum number of iterations.

This makes a good first workload because every implementation is easy to inspect, but the performance behavior is not trivial. A small change in how we compute distances can change memory by hundreds of megabytes. A Python loop is very readable, but it pays interpreter overhead. Numba and JAX both compile, but they pay different first-call costs. And when K and d grow, a trick that looked unnecessary at small size can suddenly become important.

The reference/optimized split

Reference behavior

  • Same initial centroids across implementations.
  • Compare final inertia and iteration counts.
  • sklearn fixed-init check passes: relative inertia difference about 1.5e-16.

Optimization questions

  • Does vectorization create an O(N*K*d) temporary?
  • Can Numba compile the scalar loop cleanly?
  • Does JAX compile enough work to pay for tracing?

Files: experiments/kmeans/kmeans_numpy.py, kmeans_numba.py, kmeans_jax.py, check_sklearn_equivalence.py.

The first thing I want to protect is the meaning of the result. K-means can look different just because the initial centroids are different, so every implementation in this repo receives the same initial centroids. Then we compare final inertia and iteration counts. I also added a small sklearn fixed-init check, where scikit-learn is given those same initial centroids. The relative inertia difference is about 1.5e-16, which is just floating point noise.

Only after that equivalence check do I ask optimization questions. The big one for NumPy is whether vectorization creates an O(N*K*d) temporary. For Numba, the question is whether the scalar loop can be compiled cleanly without fighting the compiler. For JAX, the question is whether the computation is large and regular enough to pay for tracing and XLA compilation.

Here are the main k-means numbers for the small-shape case: K equals 5, d equals 10, and max_iter equals 30. At one million rows, the naive NumPy implementation takes about 5.22 seconds. Numba takes 0.482 seconds, and JAX takes 0.499 seconds. So on this CPU, the compiled paths are very close at the largest size, and both are about ten times faster than naive NumPy.

The memory number is just as important as the runtime number. Naive NumPy peaks around 810 MiB in tracemalloc because it creates the broadcasted distance tensor. That tensor has shape N by K by d. It is mathematically clear, but it is not memory friendly.

Notice that NumPy matmul is not always faster here. At small K and small d, the matrix multiply form has overhead and does not automatically win. This is one of the main lessons: vectorization is not a magic word. The shape of the computation decides whether the trick pays off.

When presenting a table like this, I do not want to read every cell. I want to point to the pattern. At small sizes, overheads dominate. At large sizes, memory shape and compiled loops dominate. The useful result is not a single number, but knowing when the ranking changes.

k-means runtime scaling

The pure Python loop point at N=2,000 shows the interpreter-overhead gap that CPython JITs target. Numba and JAX are compiled numerical paths.

This plot shows the same story on a log scale. The purple point is the pure Python loop at only N equals 2,000. It is already slow enough to sit in a completely different regime. That is the kind of interpreter overhead that a future CPython JIT could target.

But we should be precise about the boundary. A CPython JIT would speed up Python bytecode. It does not change the algorithm, and it does not make a NumPy C loop or a BLAS call faster. In this local environment, the 3.14 JIT is not available, so the honest conclusion is: the JIT story is interesting, but not measured here.

For measured CPU performance today, Numba is the strongest path for this loop-heavy kernel. JAX catches up at the largest size, but it has a first-call cost and a stricter programming model.

When K and d grow, the story changes

K=50, d=100, max_iter=10. NumPy naive is capped at N=5,000 because the broadcast temporary is O(N*K*d); matmul is 5.5x faster than naive at that small point.

Now I change the shape of the same experiment. K becomes 50 and d becomes 100. This is closer to the shape of some real EM-style workloads, where each iteration compares points to many parameter vectors in a higher-dimensional space.

Here the NumPy matmul identity becomes useful. At N equals 5,000, matmul is already about 5.5 times faster than naive broadcasting. I do not run naive NumPy at the larger sizes because the temporary array grows as N times K times d, and that would turn the benchmark into a memory stress test rather than an algorithm comparison.

This is the practical message: the right optimization is conditional. For skinny K and d, matmul may not help much. When K and d grow, the same identity can be the difference between a reasonable program and a giant temporary.

k-means takeaways

NumPy

Vectorization can move work to C, but it may create large temporaries. The matmul identity pays when K*d is large enough.

Numba

Best CPU ROI for scalar numerical loops: one process, small memory, Python-like code after restrictions.

JAX

Competitive when the computation maps cleanly to array programs; first-call tracing remains a real cost.

For k-means, I would summarize the trade-off this way. NumPy is the best starting point because it is readable, debuggable, and close to the math. But vectorization can silently move the bottleneck from Python time into memory allocation. You still need to think about the shape of intermediate arrays.

Numba has the best CPU return on investment here. If the hotspot is scalar numerical loops over arrays, it lets us keep one process, avoid large temporaries, and compile the inner loop. The restrictions are real, but for this kind of kernel they are manageable.

JAX is competitive when the computation is regular and array-programmable. I would not use this CPU result alone as the main reason to adopt JAX. I would use JAX when the larger plan includes batching, differentiability, or accelerators.

Workload 2

Permutation tests as resampling pressure

The statistic is simple, but simulation demands thousands or millions of resamples. That turns memory copies, random generation, and parallel overhead into the real bottlenecks.

The second workload is a permutation test. This is a good contrast with k-means because the statistic itself is simple. We take two groups, compute a difference of means, shuffle labels under the null hypothesis, and repeat many times to approximate the null distribution.

The computational pressure is different. There is no long dependency chain like k-means. Instead, we have many independent resamples. That sounds embarrassingly parallel, but the moment we implement it, we have to answer engineering questions: where does the data live, who owns the random generator, how much memory do processes copy, and does the parallel framework cost more than the work it runs?

Attack the statistic before the runtime

Naive view

Shuffle the full vector R times, split into two groups, recompute the difference of means.

Subset-sum view

Since sum(x) is fixed, the statistic only needs S1, the sum of the selected group-A indices.

In plain NumPy, choice(replace=False) still behaves like permutation internally. The idea matters most when it changes batching, memory, or accelerator mapping.

Before reaching for a runtime, we should ask whether the statistic itself can be simplified. The naive view says: for every resample, shuffle the full vector, split it into two groups, and recompute the difference of means.

But the total sum of x is fixed. If S is the total sum and S1 is the sum of the selected group-A indices, then the difference of means can be written entirely in terms of S1. So conceptually, we do not need a full shuffled vector. We only need the subset of indices that goes into group A.

There is an important caveat. In plain NumPy, choice without replacement still behaves a lot like permutation internally, so this idea does not automatically speed up the simple loop. But the idea changes the mental model. It becomes useful when it changes batching, memory layout, or accelerator mapping. This is why statistical algebra comes before parallel programming.

Here are the permutation results at n equals 10,000 and R equals 10,000. The plain NumPy loop takes 0.856 seconds. The standard ThreadPool implementation on the GIL build takes 0.392 seconds, which is already a 2.2x improvement. That can happen because some NumPy operations release the GIL while they work in C.

The same thread implementation on the free-threaded Python build takes 0.173 seconds. That is not a rewrite. It is the same basic thread pool idea with a different interpreter ceiling. Multiprocessing, on the other hand, takes 1.71 seconds and carries about 833 MiB of child-process RSS. For this medium-sized run, process startup and copies dominate.

Numba prange is the fastest measured CPU path at 0.064 seconds, about 13.4x faster than the NumPy loop. JAX vmap on CPU is the honest anti-pattern here: 37 seconds. That does not mean JAX is bad. It means this random-permutation workload is not a good CPU XLA workload.

The important contrast is that the same statistical operation creates very different systems behavior. One version is limited by Python loops, one by process overhead, one by random generation inside compiled code, and one by XLA doing a poor job on this CPU pattern. That is why I prefer to describe workloads by shape rather than by library name.

Runtime scaling and memory footprint

Processes hide copies in child RSS. Batched NumPy hides cost in temporary arrays. Numba and threads keep one shared input array.

The left plot shows runtime scaling as R grows. Numba stays far below the other CPU implementations. Multiprocessing has a visible floor because starting processes and moving data have a cost before useful work happens. JAX grows badly here on CPU, which is why I keep calling it an anti-pattern for this particular case.

The right plot is the memory story. Some memory costs are obvious, like a giant batched NumPy array. Some are easy to miss. Multiprocessing does not necessarily show the full cost in the parent process, so I measure child-process RSS separately. That is where the 833 MiB number comes from.

This is the reason shared memory matters. For resampling workloads, threads and Numba can keep one input array in the process. Processes can be robust and portable, but they need an explicit memory budget.

Free-threaded Python makes the thread story concrete

The same ThreadPoolExecutor implementation at R=10,000: py312 GIL reaches 0.32s at 8 workers; py314t free-threaded reaches 0.17s.

This slide isolates the thread question. I run the same ThreadPoolExecutor implementation with 1, 2, 4, and 8 workers under a standard Python 3.12 GIL build and a local Python 3.14t free-threaded build.

At one worker, the two builds are similar. At two workers, they are also close. At four and eight workers, the free-threaded build keeps improving, while the GIL build flattens out. At eight workers, py312 reaches about 0.32 seconds, and py314t reaches about 0.17 seconds.

The interpretation is not that free-threaded Python makes every program faster. It removes one ceiling. If the workload still has shared mutable Python objects, locks, or bad memory locality, you can still lose. But for this thread-friendly resampling code, the no-GIL build gives the same code a higher ceiling.

Permutation takeaways

Processes

Standard and robust, but startup cost and worker copies can dominate medium simulations.

Threads

Shared arrays are the point. Free-threaded Python improves the same code when Python-level work remains.

Numba

For this CPU kernel, prange is the clear winner, but parallel RNG design becomes part of correctness.

For permutation tests, the decision is different from k-means. Processes are standard, robust, and easy to reason about, but they can pay startup cost and carry worker copies. That is acceptable for huge jobs, but it is expensive for the medium simulations that many people run interactively.

Threads are interesting because the input array is shared. In old Python, that was only useful when the heavy work released the GIL. In free-threaded Python, the same design becomes more generally useful, as long as the code avoids shared Python-state contention.

Numba wins this CPU kernel because it compiles the loop and parallelizes inside one process. But it also makes random number generation part of correctness. If parallel streams are correlated, your p-values can be wrong even when the code is fast.

Developer experience traps we hit

JAX timing Without block_until_ready, you benchmark dispatch instead of computation.
JAX CPU vmap Vectorizing random permutations on CPU is an anti-pattern here; it is not a universal parallel loop replacement.
Numba RNG Parallel random streams need high-quality per-iteration seeds; correlated streams can shift the null distribution.
Benchmark isolation Run each implementation in a subprocess, or one 2 GiB allocation can poison the next measurement.

Here are the traps that mattered most in practice. First, JAX timing. If you do not call block_until_ready, you can accidentally benchmark dispatch instead of computation. That makes the code look much faster than it really is.

Second, JAX vmap is not a universal parallel loop replacement. It is excellent when the workload maps well to XLA and especially when an accelerator is involved. But vectorizing random permutations on CPU was the wrong shape here.

Third, Numba random number generation requires care. In an earlier version of this experiment, a naive per-iteration seed scheme introduced a visible shift in the null distribution. The code was fast, but the simulation check caught that it was statistically wrong. That is exactly why we started with controlled experiments.

Finally, benchmark isolation matters. A big allocation or a compiled function from one run can change the next run. Running each implementation in a subprocess is boring, but it keeps the evidence honest.

These are not abstract warnings. Each one came from building or checking this repo. That is why I like experiments that are small enough to rerun locally. They turn vague advice into concrete failure modes that you can show, fix, and document.

No single winner

Runtime and memory are measured from sweeps. Debuggability and effort are speaker-assigned after implementing the variants.

This chart is intentionally not a crown. It is a reminder that speed is only one axis. NumPy is not always fastest, but it is usually the easiest place to debug and validate a statistical idea. Numba can be extremely fast on CPU loops and can save memory by avoiding temporaries, but it adds compiler restrictions and sometimes awkward debugging. JAX has a powerful model when the computation is array-programmable or accelerator-bound, but it asks for a more functional style and has sharp timing pitfalls.

So if someone asks, which tool should I use, my answer is: first tell me the computational pattern and the validation contract. A tool choice without those two pieces is just a preference.

There is also a team dimension here. The best tool for a one-off research notebook may not be the best tool for a shared package used by collaborators. Debuggability, installation cost, and the ability to explain the method can matter as much as the last factor of two in runtime.

Decision guide

Start Write the clearest NumPy or Python reference and define the statistical checks before optimizing.
Use Numba When the bottleneck is numerical loops over arrays and CPU is the target.
Use threads/no-GIL When repeated work can share large in-process arrays and process copies dominate.
Use JAX When the workload is array-programmable, batching-friendly, or headed to accelerators.
Be honest If the local JIT or GPU is unavailable, say that clearly and do not infer speedups as measured results.

Here is the decision guide I would use after these experiments. Start with the clearest reference implementation. That is where you define the statistic, the expected behavior, and the correctness checks.

Use Numba when the bottleneck is numerical loops over arrays and CPU is the target. That was the best return on investment for both the k-means scalar loop and the permutation prange kernel.

Use threads, and consider free-threaded Python, when repeated work can share large in-process arrays and process copies dominate. That is the key advantage we saw in the permutation test.

Use JAX when the workload is array-programmable, batching-friendly, differentiable, or headed to accelerators. Do not assume that CPU vmap over any loop will be fast.

And be honest about the environment. If the local JIT or GPU is not available, say that clearly. Do not report hoped-for speedups as measured results.

You do not have to memorize this table. The workflow is the memory aid. First make a reference you trust. Then find the expensive pattern. Then choose the smallest tool that removes that pattern without changing the statistic. If that tool is plain NumPy, great. If it is Numba, threads, or JAX, use it with the right measurement contract.
