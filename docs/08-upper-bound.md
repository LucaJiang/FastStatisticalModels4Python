如果不考虑开发与维护的工程量，只关注**核心数值计算在运行时的极限速度**，那么这些技术最终能生成的机器码质量，决定了它们的效率上限。

下面按**性能潜力**从高到低，分成五大梯队来详细说明。

---

### 第一梯队：手写 C/C++（通过 CPython API 或 pybind11）
**理论性能：达到 CPU 的绝对峰值性能（手工 SIMD / 汇编）**
这是天花板。你直接用 C/C++ 写出最核心的计算内核，编译后可获得与机器硬件完全匹配的指令流。
- **手工调优**：你可以手动使用 AVX-512、ARM NEON 等 SIMD 指令，精确布置缓存预取、循环展开，甚至写入少量汇编。这使得内存带宽和浮点运算单元能被 100% 压榨，理论上可达到处理器的**浮点峰值吞吐量**（例如每周期 32 次浮点运算）。
- **pybind11** 本身不增加计算开销，它只是一个很薄的绑定层，函数调用被直接转发到 C++ 代码。因此，如果 C++ 内核已经手工优化到极致，那么从 Python 调用的运行效率就等同于**极致优化的 C++**。
- **CPython API** 同理，但在数值计算时，你必须尽快离开 Python 对象，在纯 C 数组上运算，避免任何 `PyObject` 操作，这样才能达到此上限。

### 第二梯队：Cython 与 Numba、JAX（使用强大编译器但无手工 SIMD）
**理论性能：非常接近硬件极限（依赖编译器的自动向量化）**
这三者都能生成高质量的本地机器码，但由于依赖**编译器的自动优化**，无法像手工那样强制使用某些指令。它们的峰值性能通常能达到手工优化代码的 80-100%。

- **Cython**：当你给所有变量都加上精确的 C 类型，并在循环内只进行纯 C 运算时，它会被翻译成 C 代码，再通过 GCC/Clang 编译。此时它**就是 C**，性能直接取决于 C 编译器的优化能力。现代编译器自动向量化很强，因此它能轻松达到接近峰值的性能。
- **Numba**：它的 JIT 模式（`nopython=True`）使用 LLVM 后端，能对带类型标注的循环进行**自动向量化**，生成极佳的 SIMD 代码。在许多数值基准测试中，Numba 生成的代码与手写 C 或 Fortran 的速度**几乎无差别**，同样能触及处理器极限附近。
- **JAX**：使用 XLA 编译器，会在整个计算图上进行激进的算子融合、内存重用和自动并行化。即便是在 CPU 上，XLA 也经常能生成比普通手写循环更优的代码（例如彻底消除中间数组）。对于矩阵运算和大规模张量操作，它的 JIT 版本同样能达到**机器峰值带宽或算力**。
- **这三者的细微差距**：通常 JAX 的主动融合优化在某些场景下可超越简单手写的 C 循环；Numba 在循环密集型但难以融合的任务上可能略优于 JAX；Cython 在调用外部 C 库时最自然。但极限都在同一个量级。

### 第三梯队：NumPy（静态 C/Fortran 库，但受限于数组表达式）
**理论性能：向量化操作可达峰值，但通用算法无法达到**
NumPy 本身不是一个编译工具，而是一个**事先用 C/Fortran 编写的高性能库**。
- 当你写出 `a + b * c` 这样的向量化表达式时，背后的 ufunc 和 BLAS 库是手工极致优化的代码，你的 CPU 同样在满负荷运转。很多运算可以达到硬件极限。
- **无法避免的瓶颈**：如果你的算法**无法完全向量化**，例如需要根据条件在循环内动态改变数组形状，那么 NumPy 会迫使你退回到 Python 循环（慢数千倍），或者创建大量不必要的临时数组来拼凑操作。这种时，内存带宽的巨大浪费会让它无法达到理论峰值，而第一、第二梯队的工具可以通过循环融合直接做到最优。

### 第四梯队：PyPy（通用 JIT，不专门优化数值）
**理论性能：相当于朴素 C 代码的循环，无自动向量化**
PyPy 的跟踪 JIT 可以把纯 Python 的数字循环编译为机器码，并消除整型、浮点型的装箱开销。
- 它能达到**接近朴素 C 语言循环**的性能（如果你用 C 写一个简单的 `for` 循环而不加任何优化选项）。
- 但它**不会**进行 SIMD 自动向量化，也无法利用 FMA 指令做单指令多数据运算。因此对于密集矩阵乘法等，其峰值效率远低于第一、二梯队，可能只达到硬件峰值的 **10-30%**（取决于操作强度）。
- 它的定位是让“不用 NumPy 的纯 Python 数值代码”跑得飞快，但绝不是追求极限计算的首选。

### 第五梯队：CPython 3.13+ 实验性 JIT
**理论性能：仅消除解释器循环开销，与数值加速无关**
它的任务是"把一条字节码指令直接换成一小段机器码"，以避免解释循环的分派和译码开销。
- 它**不会**做任何数值循环优化、类型推断或向量化。
- 因此，一段典型的 Python 数值循环在它上面，可能只比纯 CPython 解释执行快 **5-15%**。它的性能与以上所有工具存在数量级的差距，完全不是为极限数值效率设计的。

---

### 最终的效率结论

如果完全不考虑工程量，以让 CPU 在数值运算上 “跑满” 为目标，排序如下：

1. **绝对王者**：**手写 C/C++ 扩展 + 手工汇编/SIMD**（通过 CPython API 或 pybind11 暴露）。这是人类能写到的最优机器码，理论效率 = 硬件物理极限。
2. **极限挑战者**：**Cython、Numba、JAX**。在 99% 的实际案例中，它们生成的代码与手工优化几乎无差别，都能触及硬件峰值，且 JAX 在图融合上还可能反超简单手写循环。
3. **特定条件下可比肩**：**NumPy**。仅当能把所有计算都完美表达为武器库里的向量化函数时，才能跑出第一梯队的性能。
4. **通用优化**：**PyPy**，可达朴素 C 的速度，但无法进行向量化极致压榨。
5. **几乎无加速**：**CPython 实验性 JIT**。

**一言以蔽之：手写 C（带 intrinsics）拥有最高的理论上限，而 Numba/JAX/Cython 是无需手动管理指令集就能无限逼近该上限的最强自动工具。**
